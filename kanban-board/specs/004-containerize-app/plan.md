# Implementation Plan: Containerized Kanban App

**Branch**: `004-containerize-app` | **Date**: 2026-11-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/004-containerize-app/spec.md`

## Summary

Add an optional Docker Compose way to run the whole kanban app with one command and only Docker on
the host. The backend becomes a multi-stage `python:3.12-slim` image (dependencies installed with
`uv` from the existing lockfile, run by `uvicorn` as a non-root user, with a healthcheck that hits
the database). The frontend is built with Vite in a Node stage and served by non-root nginx, which
also proxies `/api`, `/docs` and `/openapi.json` to the backend. Because the build sets
`VITE_API_BASE_URL` to an empty string, the browser uses relative URLs, so the image has no
environment-specific API address and needs no CORS. Only nginx publishes a port, bound to
`127.0.0.1:8080` by default. Data lives in the named volume `kanban-data`. Settings come from
`KANBAN_*` variables (shell or root `.env`, template in the versioned `.env.example`), with defaults
so no `.env` is needed. Each project gets a `.dockerignore`. The existing E2E suite runs unchanged
in its external mode from a Playwright container against a throwaway Compose project
(`scripts/e2e-docker.sh`), and can also run from the host with `BASE_URL` pointing at a Compose app.
No backend, frontend or E2E source code changes.

## Technical Context

**Language/Version**: Python 3.12 (backend image), Node 24 LTS (frontend build stage only),
nginx 1.x stable (frontend runtime), Node + Playwright 1.64.1 (E2E runner image); Dockerfile syntax
1 (BuildKit); Compose Specification; POSIX `sh` for the two scripts.

**Primary Dependencies**: Base images only — `python:3.12-slim`, `ghcr.io/astral-sh/uv` (build
stage), `node:24-slim` (build stage), `nginxinc/nginx-unprivileged:*-alpine`,
`mcr.microsoft.com/playwright:v1.64.1-noble`. No new Python or npm packages.

**Storage**: Existing SQLite file, moved for containers to `/data/kanban.db` on named volume
`kanban-data` (WAL mode as today). Non-container `backend/kanban.db` unchanged.

**Testing**: Existing pytest, Vitest and Playwright suites unchanged. New: `scripts/e2e-docker.sh`
(Playwright suite inside Compose) and `scripts/docker-smoke.sh` (container-level checks, written
first and seen to fail). See [research.md R14](research.md#r14-verification-approach-principle-iv-for-infrastructure).

**Target Platform**: Linux containers on `linux/amd64` and `linux/arm64` hosts (Docker Desktop on
macOS/Windows, Docker Engine on Linux). Docker Engine ≥ 25 (needed for healthcheck `start-interval`), Compose ≥ 2.24.

**Project Type**: Web application (existing `backend/` + `frontend/` + `e2e/` monorepo); this
feature adds deployment/packaging files only.

**Performance Goals**: Warm start to usable board < 30 s; cold first build < 10 min (SC-002). Board
behaviour as today (nginx adds no measurable latency locally).

**Constraints**: One published host port, loopback by default; image tags set by
`KANBAN_IMAGE_TAG` (default `local`) so the smoke and E2E scripts never retag the user's images;
non-root processes; no secrets,
tests, local DBs or dependency folders in images; one uvicorn worker (SQLite write serialization);
no API/contract/UI changes; non-container workflow untouched; containers stay optional
(Principle V).

**Scale/Scope**: Single user, local machine or trusted host. 3 Dockerfiles, 3 `.dockerignore`, 1
nginx template, 2 Compose files, 2 scripts, `.env.example` + README updates.

**Structure Decision**: Keep the existing three-project monorepo. Each project owns its

image, so it lives in `frontend/nginx/`.

## Implementation notes for tasks

- **Order (test-first)**: write `scripts/docker-smoke.sh` and `scripts/e2e-docker.sh` + `compose.e2e.yaml`
  first and see them fail (no images/compose) → `.dockerignore` files → backend Dockerfile →
  frontend Dockerfile + nginx template → `compose.yaml` → smoke green → E2E green → docs.
- **Pin** every base image to a specific tag (and the `uv` image version); the Playwright image tag
  must equal `@playwright/test` in `e2e/package-lock.json`. Note this coupling in `e2e/README.md`.
- **Dockerfile conventions** (docker-build-strategies): `# syntax=docker/dockerfile:1`, named stages,
  `WORKDIR` first, bind-mounted manifests + cache mounts for `uv`/`npm`, `COPY --link
  --chown=<uid>:<gid>`, `USER` after file ops, exec-form `CMD`, `EXPOSE`, OCI `LABEL`s.
- **Compose conventions** (docker-compose-patterns): pinned images via build, `depends_on` with
  `service_healthy`, healthchecks on both services, named volume declared top-level, default network,
  no `env_file`, `${VAR:-default}` everywhere, `restart: unless-stopped`.
- **Destructive commands** (docker-destructive-guardrails): `down -v` appears only as the documented
  reset command and inside the scripts against their hard-coded throwaway projects
  (`kanban-e2e`, `kanban-smoke`); docs label reset as destructive. Implementation must not run
  `down -v` on project `kanban` or any prune command.
- **Docs**: root README gains "Run with Docker" (prerequisite + versions, start/stop/reset, address,
  `KANBAN_*` table, network warning, first-build time, E2E command); `e2e/README.md` gains
  "Run in Docker" and the host-to-Compose example; `frontend/README.md` notes that the container
  build uses relative API URLs.

## Complexity Tracking

| Addition | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Docker/Compose as an optional run path (Principle V lists "containers required to run") | Spec goal: run with only Docker; base for deploy | Not required to run: every non-container command is unchanged, so the rule is respected; nothing simpler meets FR-001. |
| nginx (frontend runtime image) | Serve the static build in production mode (FR-013) and give one address for app + API + docs (FR-002) | Vite dev/preview server is not production mode; serving `dist/` from FastAPI couples projects and changes backend code. |
| `uv` image in backend build stage | Install exactly the locked versions from `uv.lock` | `pip` would need an exported requirements file — a second source of truth for versions. |
| Playwright image for the E2E runner | FR-012: E2E with only Docker on the host | Host Node + browsers is what FR-012 removes; the image is the official one matching the locked version. |
| Two shell scripts | One command each for E2E (with guaranteed teardown and evidence copy) and for container checks (Principle IV) | Raw multi-step Compose commands can't guarantee cleanup on failure; a Makefile needs `make`; test frameworks for containers add dependencies. |
