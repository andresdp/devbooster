# UX Requirements Checklist: Kanban Web Frontend

**Purpose**: Validate that the interaction and visual requirements (screens and states, error placement, drag-and-drop states and their alternatives, responsive behaviour, accessibility) are complete, unambiguous, consistent and measurable before implementation starts
**Created**: 2026-10-25
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [contracts/routes-and-views.md](../contracts/routes-and-views.md) · [research.md](../research.md) · [design/](../design/README.md)
**Depth**: Standard · **Audience**: PR reviewer of the spec/plan before `/speckit-tasks` and `/speckit-implement`

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

Source abbreviations: `Spec §FR-nnn` / `§US-n ASm` / `§EC-nnn` / `§SC-nnn` / `§AS-nnn` = spec.md; `Views` = contracts/routes-and-views.md; `Research §n` = research.md; `Design` = design/design-system.md; `Model §n` = data-model.md.

## Screen & State Coverage (Stitch design or explicit rule)

- [ ] CHK001 Does the requirement set name, for every view/state the Stitch screens lack (board list page, page-level loading, page-level error, board not-found, ticket not-found inside the drawer, phone-width layout, move-from-detail control), the concrete visual rule it follows, rather than only "stay visually consistent"? Research §1.4 derives the board list and move control but gives no rule for `ErrorState`, `NotFoundState` or the drawer's not-found state. [Completeness, Spec §FR-020, Research §1.1, Gap]
- [x] CHK002 Is the board list layout specified unambiguously? `Views` says "one row/card per board", which allows two different layouts; the row contents (name, created time) and the position of the "New board" control need a single stated form. [Clarity, Views §BoardListPage, Research §1.4]
- [x] CHK003 Are the loading skeletons specified in enough detail to be reviewed against the design (which elements are skeletonised on the board list and on the board page, approximate shape count, pulse animation), or is the Board View skeleton preview declared the single reference for both? [Clarity, Views §BoardListPage/§BoardPage, Research §1.3]
- [ ] CHK004 Is the content of the `ErrorState` and `NotFoundState` views specified (icon, heading text, where the server message appears, label and target of the Retry/back control) so they can be built without inventing copy? [Completeness, Spec §US-1 AS7/AS8, Spec §FR-017, Views §Routes, Gap]
- [ ] CHK005 Are the drawer's comments and history loading, error and empty states defined with placement and appearance ("inline message + retry" has no stated position, size or relation to the tab content), consistent with the page-level `ErrorState`? [Completeness, Views §TicketDrawer States, Gap]
- [x] CHK006 Is the precedence chain between design sources stated in one place and free of contradiction: live Stitch project (Spec §AS-002 "source of truth") vs. frozen snapshot (design/README "fixed reference for SC-006") vs. design-system prose vs. exported screens vs. spec/contract (Research §1.4, Design note)? - [ ] CHK007 Can "visually consistent in layout, colour and typography" (SC-006) be objectively judged, e.g. by requiring the token set in `design/design-system.md` to be the only colours/typography used and the component inventory in Research §1.3 to be the reference for each element? [Measurability, Spec §SC-006, Spec §FR-020]
- [ ] CHK008 Are interaction states (hover, focus-visible, active, disabled, pending) defined for every interactive element class, not just the card hover and the primary/ghost button hover named in the design prose? Links in the board list, badges (non-interactive?), tabs, segmented control options, select, close/clear icon buttons and the column dots have no stated states. [Completeness, Design §Style guidance, Gap]
- [x] CHK009 Is the appearance of the "pending" indication required by FR-016 specified for each action (create, edit Save, Move from detail, Add comment, drag commit): disabled button only, spinner, label change, form-level overlay? "disabled while pending" appears only for `BoardCreateDialog`. [Clarity, Spec §FR-016, Views §BoardCreateDialog, Gap]
- [x] CHK010 Is it specified whether the "New board" control in the shared `AppHeader` is available on the board page as well as the board list, and if so where the create dialog's success navigation and error placement apply from there? Spec §FR-002 ties creation to the list only. [Ambiguity, Spec §FR-002, Research §1.3 AppHeader, Views §BoardListPage]
- [x] CHK011 Is the drawer's view-mode/edit-mode split (an "Edit" button revealing `TicketEditForm`) a stated requirement, and is it defined which mode the drawer opens in, what Cancel returns to, and what happens to unsaved edits when the drawer is closed via Escape, the close button, or browser back? Spec §FR-007 describes one form with Save/Cancel but no mode toggle. [Ambiguity, Spec §FR-007, Spec §US-3 AS2, Views §TicketDrawer]
- [ ] CHK012 Is the dialog behaviour at phone width specified (full-screen vs. centred with margins, scroll of long content, keyboard-open viewport), given the design only defines centred `max-w-lg` dialogs on desktop? [Completeness, Design §Dialogs, Spec §FR-019, Gap]

## Error Placement & Messaging Clarity

- [x] CHK013 Does the placement rule cover every error code the client can receive, each in each situation (page load vs. user action)? Codes known from Model §2: `validation_error`, `not_found`, `conflict`, `invalid_move`, `internal_error`, `http_error`, plus client codes `network_error`, `unexpected_response`. The `Views` table omits `unexpected_response`, `internal_error` by name, `conflict` outside board creation, and `not_found` on an action (e.g. editing or commenting on a ticket deleted elsewhere). [Completeness, Spec §FR-014, Spec §SC-004, Views §Error placement contract, Gap]
- [x] CHK014 Is the rule for matching `details[].field` to a visible form field stated (exact name match, case, whether a path prefix such as `body.title` is stripped), so that "field the form does not display" (EC-002) is decidable? [Clarity, Spec §EC-002, Spec §FR-014, api-client §Error mapping, Gap]
- [x] CHK015 Is the combined display defined when one response contains both mappable and unmappable details: field messages beside fields plus `error.message` and the leftover messages at form level, with no message shown twice? [Clarity, Views §Error placement contract, api-client §fieldErrors]
- [x] CHK016 Are the lifecycle rules for each error surface defined: when a field error clears (on change, on resubmit), when a `FormError` clears, whether errors persist when a dialog is closed and reopened, and whether `BoardNotice` ("cleared on next successful action") also clears on close, navigation or timeout? [Completeness, Spec §FR-014, Spec §FR-015, Views §BoardPage notice, Gap]
- [x] CHK017 Is the error surface for a failed move-from-detail unambiguous? The table assigns action errors to "the `FormError` of the form that triggered it, or `BoardNotice` for drag-and-drop moves"; the `<select>` + "Move" control is neither a form nor a drag. [Ambiguity, Spec §FR-011, Spec §FR-014, Views §Error placement contract]
- [x] CHK018 Is the follow-up behaviour after an action-level `not_found` or `conflict` specified (e.g. refresh the board, close the drawer, keep the entered values), matching what EC-004 specifies only for `invalid_move`? [Coverage, Spec §EC-004, Spec §FR-010, Gap]
- [ ] CHK019 Is the position of "near the board" for move errors fixed in the requirements (Research §1.4 chooses the top of the board area in place of the design's top-right toast), and is its behaviour on phone width (sticky, above the snapping row, obscuring the first column?) specified? [Clarity, Spec §FR-010, Spec §US-4 AS5, Research §1.4, Gap]
- [x] CHK020 Are the client-authored texts ("Required", "Could not reach the server.", "Unexpected response from the server (<status>).", not-found and empty-state copy) enumerated in the requirements and reconciled with AS-008 ("does not maintain its own catalogue of error texts")? [Consistency, Spec §AS-008, Spec §FR-023, Views §Error placement contract, api-client §Error mapping]
- [ ] CHK021 Are the visual specs for the three error surfaces complete and distinct: field error (error ring + `label-sm` line with icon, per Design), `FormError` banner (error-container, icon, title + message), `BoardNotice` (white panel, error icon, close), and `ErrorState` (unspecified)? [Completeness, Design §Inputs, Research §1.3, Gap]

## Drag-and-Drop State Requirements

- [ ] CHK022 Is the placeholder behaviour unambiguous during a drag: does "Drop ticket here" occupy the card's original slot, the hovered target slot, or both (`Views` says "original/target slot"; Research §7 says siblings shift to open the gap and the original node becomes the placeholder)? Is the design's "(pos 0)" position label part of the required appearance? [Ambiguity, Views §TicketCard, Research §1.3, Research §7, Design §Drag]
- [ ] CHK023 Are the placeholder's appearance and size defined for every drop context: between cards, at the top, at the end of a column (EC-009), and in an empty column (does it replace `ColumnEmptyState`?), and do column count chips update during the drag or only after commit? [Coverage, Spec §EC-009, Spec §US-4 AS3, Gap]
- [x] CHK024 Are the card modifiers consistently defined across documents? `Views` describes `reverting` as "rollback in progress"; Research §1.3 shows the design's "Reverting move…" ghost while rollback + refetch run; Model §3 applies `reverting`/`saving` while *committing* only after 300 ms. Each phase (committing, rollback, reload after `invalid_move`) needs one stated card appearance. [Conflict, Views §TicketCard, Research §1.3, Model §3 Drag lifecycle]
- [x] CHK025 Is the rollback transition specified (instant snap back vs. animated return, duration), and is the 300 ms flicker threshold a requirement that tests can observe or an implementation note? [Clarity, Spec §FR-010, Spec §US-4 AS5, Model §3, Gap]
- [x] CHK026 Are the allowed interactions while a move is committing stated beyond "a second drag is ignored": opening a card, creating a ticket, using move-from-detail, navigating away (EC-008 for in-flight saves)? [Coverage, Spec §FR-016, Spec §EC-008, Model §3, Gap]
- [ ] CHK027 Is dragging defined as disabled or enabled while the modal drawer is open (focus trap + `aria-modal` imply the board is inert), and is the behaviour of a drop onto the drawer or its backdrop specified? [Gap, Views §Accessibility baseline, Spec §EC-010]
- [ ] CHK028 Is the click-versus-drag disambiguation on the card (a link/button that is also the drag handle) stated as a requirement with observable thresholds (Research §7: 6 px mouse distance, 200 ms touch delay, 6 px tolerance), including that an aborted drag does not open the drawer? [Measurability, Spec §FR-006, Spec §FR-008, Research §7]
- [ ] CHK029 Is auto-scroll during a drag specified (vertical inside a 200-ticket column, horizontal when columns overflow the viewport), together with what happens when the pointer leaves the viewport? [Coverage, Spec §EC-006, Spec §SC-003, Gap]
- [x] CHK030 Is the dragged-card appearance measurable against the design (rotate 2°, scale 1.02, `shadow-drag`, key colour primary, "dragging" tag shown or dropped), and is it stated that the overlay copy, not the in-list card, carries these styles? [Measurability, Design §Drag, Research §1.3]

## Non-Drag Alternatives (keyboard, touch, move-from-detail)

- [ ] CHK031 Is keyboard drag-and-drop (focus card → Space → arrows → Space/Escape) a user-facing requirement with an acceptance scenario and specified announcements, or only a testing convenience? Spec §US-4 AS6 directs keyboard-only users to move-from-detail, while Research §7/§9 adds a `KeyboardSensor` with dnd-kit's default English live region. [Ambiguity, Spec §US-4 AS6, Spec §FR-011, Research §7, Research §9]
- [ ] CHK032 Is touch dragging on phone width specified: must in-column reorder by touch work on a 375 px screen, is cross-column touch drag expected to be impossible or merely "impractical" (EC-007), and is suppression of the long-press context menu / text selection required? [Clarity, Spec §EC-007, Spec §FR-019, Spec §SC-005, Gap]
- [ ] CHK033 Is the move-from-detail interaction fully specified: default selection of the `<select>`, "Move" pending state, what the drawer and the board show after success (column chip, card position, history tab refresh), and whether the control is hidden or disabled when a move is already committing? [Completeness, Spec §FR-011, Spec §US-4 AS6/AS7, Spec §AS-007, Views §TicketDrawer Column row]
- [ ] CHK034 Is it stated whether moving via detail refreshes the history list so US-5 AS4 holds without reopening the ticket, and whether `Comments (n)` / `History (n)` counts refresh accordingly? [Consistency, Spec §FR-013, Spec §US-5 AS4, Views §TicketDrawer Tabs, Gap]

## Accessibility Expectations

- [x] CHK042 Is the accessibility baseline in `Views` traceable to a stated requirement or explicit decision (the spec has no accessibility FR and no exclusion), so reviewers know whether it is a quality gate or optional? [Traceability, Views §Accessibility baseline, Spec §Requirements, Gap]
- [x] CHK043 Is initial focus specified for each dialog and for the drawer in both open paths (from a card click and from a direct address load): first field, heading or close button? [Completeness, Views §Accessibility baseline, Spec §FR-017, Gap]
- [x] CHK044 Is focus return specified on close for the drawer (to the originating card, or to the board heading after a direct load) and for each dialog (to the "New board"/"New ticket" button), and after mode changes inside the drawer (Save → view mode, Cancel, comment submitted and cleared)? [Completeness, Spec §FR-006, Spec §FR-007, Spec §US-5 AS2, Gap]
- [x] CHK045 Are live announcements specified for errors and status changes (`FormError`, `BoardNotice`, `ErrorState`, "Required" messages, pending/busy states, successful move or comment)? Only field errors have `aria-describedby`/`aria-invalid` defined. [Coverage, Views §Accessibility baseline, Spec §FR-014, Spec §FR-016, Gap]
- [x] CHK046 Is the card's accessible role resolved: `Views` calls it "a link/button" that is also the drag handle; is it a link to the ticket address (routing) with dnd-kit keyboard attributes, or a button, and is its accessible name defined (key + title)? [Ambiguity, Views §TicketCard, Views §Accessibility baseline]
- [x] CHK047 Are keyboard and ARIA patterns specified for the composite controls the design introduces: `Tabs` (tablist/arrow keys), `SegmentedControl` (radiogroup), the move `<select>`, the column dots, and icon-only buttons (close, clear assignee) with text labels? [Completeness, Views §TicketDrawer, Research §1.3, Gap]
- [x] CHK048 Are the focus-ring appearance (colour, width, offset, visible on `surface-container-low` inputs and on cards) and colour-contrast expectations stated or explicitly excluded, in particular for badge pairs such as `on-secondary-container` #fffbff on `secondary-container` #6063ee and `on-surface-variant` on `surface-container`? [Measurability, Design §colors, Research §1.2 enum colours, Gap]
- [x] CHK049 Is reduced-motion handling stated or intentionally excluded for the drag tilt/scale, skeleton pulse, drawer slide-in and backdrop blur? [Gap, Design §Drag, Design §Dialogs]
- [ ] CHK050 Are document titles per route and landmark structure (header, main, `<h1>` per page, `<h2>` per column) defined so reload/share (FR-017) yields an identifiable page for assistive technology and browser history? [Completeness, Spec §FR-017, Views §Accessibility baseline, Gap]
